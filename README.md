# Домашнее задание 01: Документирование архитектуры в Structurizr

## Вариант 22: Система управления событиями

### Описание системы

Система управления событиями (Event Management System) - это веб-приложение для организации и управления мероприятиями, аналогичное [Eventbrite](https://www.eventbrite.com/).

### Данные системы

Приложение содержит следующие сущности:
- **Пользователь** - зарегистрированный пользователь системы
- **Событие** - мероприятие с датой, временем, описанием и местом проведения
- **Участник** - связь между пользователем и событием (регистрация на мероприятие)

### Требования к API

Система должна реализовывать следующие API endpoints:

#### Управление пользователями
- Создание нового пользователя
- Поиск пользователя по логину
- Поиск пользователя по маске имя и фамилии

#### Управление событиями
- Создание события
- Получение списка событий
- Поиск событий по дате

#### Управление участниками
- Регистрация пользователя на событие
- Получение участников события
- Получение событий пользователя
- Отмена регистрации на событие

## Архитектурное решение

### Роли пользователей
1. **Организатор событий** - создает и управляет событиями
2. **Участник** - регистрируется на события и управляет своими регистрациями
3. **Администратор** - управляет пользователями и системой

### Внешние системы
1. **Email Service** - отправка уведомлений о регистрации и напоминаний
2. **SMS Service** - отправка SMS-уведомлений участникам
3. **Payment System** - обработка платежей за платные события (опционально)
4. **Calendar Service** - интеграция с календарями пользователей

### Контейнеры системы

1. **Web Application** - клиентское веб-приложение для взаимодействия с пользователями
2. **API Gateway** - точка входа для всех API запросов
3. **User Service** - управление пользователями и аутентификацией
4. **Event Service** - управление событиями
5. **Participant Service** - управление регистрациями на события
6. **Notification Service** - отправка уведомлений пользователям
7. **Database** - хранилище данных (PostgreSQL)

### Технологии

- **Frontend**: React/Vue.js
- **API Gateway**: Node.js/Express или Spring Cloud Gateway
- **Backend Services**: Node.js/TypeScript или Java/Spring Boot
- **Database**: PostgreSQL
- **Message Queue**: RabbitMQ/Kafka (для асинхронных уведомлений)
- **Cache**: Redis (для кэширования списков событий)

## Диаграммы

Все диаграммы представлены в файле `workspace.dsl`:

1. **System Context (C1)** - показывает систему в контексте пользователей и внешних систем
2. **Container (C2)** - показывает внутреннюю структуру системы с контейнерами
3. **Dynamic** - показывает сценарий регистрации пользователя на событие

## Архитектурно значимый сценарий

**Регистрация пользователя на событие:**

1. Пользователь выбирает событие в Web Application
2. Web Application отправляет запрос на регистрацию в API Gateway
3. API Gateway перенаправляет запрос в Participant Service
4. Participant Service проверяет существование пользователя через User Service
5. Participant Service проверяет существование события через Event Service
6. Participant Service создает запись участника в Database
7. Participant Service отправляет событие в Notification Service
8. Notification Service отправляет подтверждение через Email Service
9. Ответ возвращается пользователю через всю цепочку
