# Проектирование документной модели данных

## Предметная область

Система управления событиями (Event Manager) - платформа для создания событий и регистрации участников.
(к сожалению я не техпис поэтому пришлось прибегнуть к иишке для более полного обоснования)

## Сущности

1. **Пользователь (User)** - пользователь системы, может быть организатором или участником событий
2. **Событие (Event)** - мероприятие с датой, местом проведения и списком участников
3. **Участник (Participant)** - связь между пользователем и событием

## Структура коллекций

### Коллекция `users`

```javascript
{
  _id: ObjectId,
  login: String,
  password_hash: String,
  first_name: String,
  last_name: String,
  email: String,
  created_at: Date
}
```

**Индексы:**
- `{ login: 1 }` - уникальный индекс для быстрого поиска по логину
- `{ first_name: 1, last_name: 1 }` - составной индекс для поиска по имени и фамилии

### Коллекция `events`

```javascript
{
  _id: ObjectId,
  title: String,
  description: String,
  date: Date,
  location: String,
  organizer_id: ObjectId,
  participants: [
    {
      user_id: ObjectId,
      registered_at: Date
    }
  ],
  created_at: Date
}
```

**Индексы:**
- `{ date: 1 }` - для поиска событий по дате
- `{ organizer_id: 1 }` - для поиска событий организатора
- `{ "participants.user_id": 1 }` - для поиска событий участника

## Выбор между Embedded и References

### 1. Организатор события (organizer_id) - **Reference**

**Решение:** Использовать reference (ObjectId) на коллекцию users.

**Обоснование:**
- Организатор - это полноценная сущность User с собственным жизненным циклом
- Один пользователь может быть организатором множества событий
- Данные организатора могут изменяться независимо от событий
- При изменении данных пользователя не нужно обновлять все события
- Размер документа события остается компактным

**Недостатки:**
- Требуется дополнительный запрос для получения полной информации об организаторе
- Можно решить через aggregation с $lookup при необходимости

### 2. Участники события (participants) - **Embedded**

**Решение:** Использовать embedded documents внутри события.

**Обоснование:**
- Связь участник-событие имеет дополнительные атрибуты (registered_at)
- Список участников всегда запрашивается вместе с событием
- Операции регистрации/отмены выполняются в контексте конкретного события
- Один атомарный запрос для добавления/удаления участника ($push/$pull)
- Нет необходимости в отдельной коллекции для связи many-to-many
- Количество участников ограничено (обычно до нескольких тысяч)

**Преимущества:**
- Атомарность операций (регистрация в одной транзакции)
- Высокая производительность чтения (один запрос)
- Простота реализации
- Естественная группировка данных

**Ограничения:**
- Размер документа MongoDB ограничен 16MB
- Для событий с десятками тысяч участников потребуется гибридный подход
- В текущей реализации это не проблема

### 3. События пользователя - **Вычисляемая связь**

**Решение:** Не хранить отдельную коллекцию, использовать запросы.

**Обоснование:**
- Список событий пользователя вычисляется через поиск по `participants.user_id`
- Индекс `{ "participants.user_id": 1 }` обеспечивает быстрый поиск
- Нет дублирования данных
- Всегда актуальная информация

**Запрос:**
```javascript
db.events.find({ "participants.user_id": userId })
```

## Альтернативные подходы

### Вариант 1: Отдельная коллекция participants

```javascript
{
  _id: ObjectId,
  user_id: ObjectId,
  event_id: ObjectId,
  registered_at: Date
}
```

**Недостатки:**
- Требуется 2-3 запроса для получения участников события
- Сложнее обеспечить атомарность операций
- Больше сетевых запросов
- Избыточная нормализация для документной БД

### Вариант 2: Денормализация с дублированием

Хранить полные данные пользователя в participants.

**Недостатки:**
- Дублирование данных
- Проблемы с консистентностью при изменении данных пользователя
- Увеличение размера документов

## Паттерны проектирования

### 1. Subset Pattern

Используется для participants - храним только необходимый минимум (user_id, registered_at), полные данные получаем при необходимости через $lookup.

### 2. Extended Reference Pattern

organizer_id - простая ссылка на пользователя. При необходимости можно расширить до:
```javascript
organizer: {
  id: ObjectId,
  name: String  // кэшированное имя для быстрого отображения
}
```

## Масштабируемость

**Текущие ограничения:**
- Максимум ~100,000 участников на событие (при 160 байт на участника)
- Для больших событий можно использовать Bucket Pattern

**Решение для больших событий:**
```javascript
{
  event_id: ObjectId,
  bucket: Number,
  participants: [...]  // до 1000 участников
}
```

## Типы данных MongoDB

**Используемые типы:**
- `ObjectId` - уникальные идентификаторы
- `String` - текстовые поля
- `Date` - даты и время
- `Array` - список участников
- `Object` - вложенные документы участников

## Валидация

Для обеих коллекций используется `$jsonSchema`:
- Обязательные поля (required)
- Типы данных (bsonType)
- Ограничения длины (minLength, maxLength)
- Регулярные выражения (pattern) для email и login
- Валидация вложенных документов

## Выводы

Выбранная модель данных оптимальна для системы управления событиями:
- Embedded participants обеспечивают высокую производительность и атомарность
- Reference на organizer избегает дублирования данных пользователей
- Индексы обеспечивают быстрый поиск по всем критериям
- Модель легко масштабируется при росте нагрузки
